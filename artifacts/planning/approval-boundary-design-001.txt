APPROVALS boundary design — 2026-10-17

Current gap

`workflow.record` refuses to clear WAITING_APPROVAL or NEEDS_REPLAN, and `snapshot` makes these holds sticky. There is no resolution path yet. The APPROVALS card correctly requires exact gate-event and artifact binding, a trusted user authorization reference, rejection of replay/fabrication, and preservation of the hold on rejection. Current SQLite triggers and immutable JSON writes only protect against ordinary mistakes: the same workspace owner can alter the DB, drop triggers, replace files, or modify the verifier. They cannot authenticate a human.

Minimal receipt flow

1. A resolver command creates an immutable approval request from the current held event. Bind a stable project/repository identity; card and gate status; SQLite event sequence; canonical hash of the full gate event payload; decision scope (pilot, final dataset, or replan); exact relevant artifact/config/implementation hashes; unique nonce; and the requested decision. Display those values for operator review. Never take the requested decision only from a workspace JSON file.
2. An operator-controlled signing step signs the canonical request plus the decision and a short explicit statement. The resulting receipt contains schema/version, key ID, request hash, decision, statement, signature algorithm, and detached signature. The private key stays outside the repository and agent-writable state. Keep requests and receipts append-only.
3. `approvals resolve` verifies the signature against a trust anchor configured outside the repository, verifies the request and current artifact hashes, confirms the referenced event is still the current unresolved gate, checks project identity and decision scope, and consumes the nonce exactly once. In one SQLite `BEGIN IMMEDIATE` transaction, append a resolution event containing hashes and signer/key ID, then append the authorized state transition. A failed check writes no clearing transition and leaves the original hold effective. A replay, stale event, changed artifact, wrong scope, unknown key, invalid signature, or reused nonce fails closed.
4. Snapshot computes a resolved hold only from a valid resolution event bound to that exact gate event and still-current hashes. A later implementation/config/artifact change makes the resolution stale and restores the hold. Ordinary `work record` remains unable to clear either hold. Preserve rejection evidence and every original event.

A practical local boundary is a user-held hardware-backed signing key whose signing operation requires user presence (for example a touch/PIN on a hardware authenticator), with its public-key fingerprint provisioned by the operator outside the checkout. The operator reviews the displayed exact hashes and signs only after deciding. A signed receipt is the authorization; JSON authorship, filename, timestamps, a self-declared `human` field, and a CLI actor label are not. Do not make a repo-controlled key file the sole trust anchor: an agent able to edit the checkout could replace both the verifier and that key. Signing can instead be delegated to an operator-controlled approval service, but that is a larger dependency.

Trust limit and required dependency

A process running as the same user on the same host cannot be cryptographically distinguished as “human” versus “agent” if both can invoke the same local software and access the same credentials. A password prompt or a locally held software key alone does not solve that problem when the worker can control the process. The required external trust dependency is one operator-controlled signer that requires a separate user-presence action and has a public key/fingerprint provisioned outside agent-writable workspace state. Until that exists, real pilot/final-dataset approvals and replan resolutions must remain blocked; do not infer approval from this design or synthetic tests.

E2E validation without counterfeit authorization

Use a disposable temporary project and generated test-only key pair to exercise valid signature acceptance, invalid/altered signature rejection, wrong event/artifact/scope rejection, nonce replay rejection, changed implementation staleness, and transaction rollback on failure. The test signer and test trust anchor are explicitly fixture-only and must never be installed in production state or accepted by the production trust store. Assert after every rejection that status remains WAITING_APPROVAL/NEEDS_REPLAN and history still contains the original gate. Assert that one valid fixture signature resolves only the exact temporary gate, and that replay leaves later/current gates held. This proves verifier and state-transition behavior, not human identity or production authorization. A real authorization requires a receipt signed through the operator-controlled signer and is separate evidence.

Smallest implementation boundary

Add a dedicated approval module and public `approvals request/resolve` commands; keep `work record` unchanged for ordinary states. Use canonical JSON plus a standard detached-signature format, bind the full decision envelope, and enforce unique nonce and current-event checks transactionally. Keep production trust configuration out of the repository and reject arbitrary per-command trust-key overrides in production mode. Add E2E-only fixture trust injection only for a disposable root; report fixture tests as deterministic protocol coverage, never as user approval. Do not add a production bypass, test-only acceptance switch, or fixture receipt to actual workflow state.

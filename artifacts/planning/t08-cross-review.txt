T08 extraction cross-review

Scope: read-only review of `src/sft/extract.py` and `tests/e2e/test_extraction.py`. This review intentionally does not repeat the already tracked fixes for expanded-text placement, CRLF/YAML fence parsing, wrapper/tab/admonition balance, or control-token quarantine.

Findings to address before T08 is considered complete

1. [P1] Bound aggregate work and output, not only each section's include expansion. `_include_expansion` initializes its `{documents, bytes}` budget when `state` is absent (extract.py:320-327), and `prepare` calls it separately for every section (around :407-414). Thus the 64-document/1 MB limit resets for every heading section and every source candidate. Many sections can repeat a valid include, while `prepare` accumulates all payloads in memory before writing. Large source reads also happen before the include byte budget (`_text` around :350), and `_sections` recomputes byte prefixes by joining all preceding lines for every section (:282-286). Add explicit per-file and per-run source-byte, include-expansion, section-count, and output-byte limits with deterministic quarantine/BLOCKED evidence; do not silently truncate. Add a public-CLI fixture with many sections/repeated includes and one oversized source to prove the bound is enforced.

2. [P1] Assert exact candidate-to-output coverage and duplicate-path rejection. `_validate_input` rejects duplicate candidate IDs but does not reject duplicate `(source_domain, source_path)` rows (:98-123); `by_path` later silently keeps only the last row for include resolution. The happy-path E2E checks source-candidate count and only that output count is at least that count (:166-169), so a regression that duplicates one candidate's sections and omits another could still pass. Reject duplicate candidate source paths and assert the emitted candidate-ID multiset is exactly the input set, with each row's domain/path/revision/source hash and span matching its source candidate.

3. [P1] Verify the committed extraction receipt in the E2E. The producer writes `record_file_sha256`, `record_count`, and per-record `record_sha256` (:454-483), but the test only parses JSONL and checks selected content; it never recomputes those hashes/counts or asks the public verifier to validate the extraction result. Add assertions for raw record-file SHA256, count, each record digest, and an isolated post-commit record mutation rejected by the public verification path. This closes a false-green gap where malformed output receipts could pass the scenario.

4. [P2] Recompute retained Git blob identity and keep source ancestry explicit. Candidate bytes are checked against source-manifest SHA256 and byte count (:139-152), while the required `git_blob` field is not checked against the actual file bytes. Recompute Git blob SHA1 (`blob <byte-count>\0<bytes>`) and add a mutated-blob-metadata rejection case. Extraction records bind their source candidate ID and source-file SHA256 but omit the eligibility/snapshot manifest hashes in each row; include those hashes (or an equally direct immutable parent reference) so detached rows retain resolvable T07/T06 ancestry.

5. [P2] Make the trusted-input boundary explicit in coverage. The configured eligibility-manifest SHA256 and the manifest's own `status == PASSED` are internally checked (extract.py:41-65), but T08 does not independently establish that this exact manifest is the current passed T07 workflow evidence; the test fixture even uses a synthetic `implementation_sha256` value. Keep deterministic fixtures for parser coverage, but add a public-path negative case showing an unpassed/stale T07 prerequisite cannot be used to claim a production T08 pass, or explicitly constrain this command to trusted local artifacts and rely on workflow prerequisite gating. Hash agreement alone proves consistency, not who authorized the manifest.

Existing useful coverage: the E2E checks UTF-8/CRLF reconstruction, section ordering, quarantine preservation, include cycles/missing/traversal/code-fence behavior, candidate tampering, and symlinked source rejection. It also now checks the included material appears once across sections. These positives do not replace the aggregate-resource, exact-coverage, or output-receipt checks above.

Resolution cross-check (read-only; current post-fix snapshot)

The implementation now addresses several production findings:
- Duplicate candidate `(domain, source_path)` pairs are rejected before `by_path` construction (`extract.py`, `seen_sources`). Candidate source files are checked for exact bytes/SHA256 and actual Git blob SHA1.
- Resource bounds now include 8 MiB per source file, 128 MiB over candidate source files, 1 MiB/64 documents of includes per candidate across its sections, and 256 MiB emitted JSONL. Source text is preserved; limit failures reject/quarantine without truncation. This is a practical bound for the frozen corpus run.
- The extraction E2E recomputes output row count, JSONL SHA256 and every row digest, and retry refuses to overwrite a mutated committed output. It also checks the inclusion expansion appears once across the document sections.
- The post-fix CRLF/Unicode physical-line test, YAML-fence metadata test and malformed-wrapper/control-token cases cover the issues parent already tracked separately.

Residual test/provenance limits to retain in the T08 result:
- Correction: `MAX_CANDIDATE_BYTES` is checked with `candidate_path.stat().st_size` before `read_bytes()` at `extract.py:99-102`; the candidate-JSONL pre-read concern is resolved. Manifest/config JSON reads still have no explicit byte cap, though frozen production manifests are small and hash-pinned.
- E2E candidate coverage currently compares sets of candidate IDs and permits `record_count >= candidate_count`; it does not assert unique `(candidate_id, section_ordinal)` pairs, contiguous ordinals, or per-row source identity against the candidate. The code generation path is direct, but the coverage assertion does not prove no duplicate output section.
- Git-blob identity is recomputed in code, but no negative fixture mutates only `git_blob` while keeping other input hashes consistent. Likewise, duplicate-path rejection and resource bounds lack focused negative cases in `test_extraction.py`. These are coverage gaps, not evidence that the current implementation fails those checks.
- Output digests are verified in the fresh E2E result. The mutation case proves immutable retry conflicts; it does not invoke a separate public extraction-verification command. Keep the distinction clear if describing this as public verifier coverage.
- The hash chain still establishes consistency, not manifest authorship. T08 checks the supplied config's T07 manifest digest and the manifest's self-reported PASSED status; it does not independently query current T07 workflow evidence. The production run must be dependency-gated through workflow state and treat the repository-local input as trusted. Do not claim cryptographic authorization from these hashes.
